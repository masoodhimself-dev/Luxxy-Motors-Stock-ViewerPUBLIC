ARCHITECTURAL DECISIONS

1. Organization and dealer hierarchy

- organizations represent the subscribing/account entity.
- dealers represent operational dealership locations.
- A single-site independent dealership has one organization and one dealer.
- Billing will normally attach to the organization.
- Features, limits and usage may be resolved per dealer with organization defaults and dealer overrides.

2. Existing vehicles

Keep the existing vehicles table and existing vehicle UUIDs as the future physical vehicle identity.

Do not rename or replace the vehicles table in this phase.

A later separately approved phase will create vehicle_listings underneath vehicles and move marketplace-specific state into those listing records.

Existing public vehicle IDs and URLs must remain stable.

3. Multi Choice Motors fixture

The attached Multi Choice Motors Motors/Cazoo JSON remains a development/test modelling fixture only.

Do not import it into Luxxy or production.

Classify the underlying provider concept as Motors Network, with Cazoo and Motors URLs retained as marketplace aliases/provenance.

4. Status authority

The CRM/manual dealership state will be authoritative for physical available/reserved/sold/hidden/archived status.

Marketplace absence may only affect a listing source state. It must never mark a physical vehicle sold.

5. Data preservation semantics

Not-observed or unavailable provider data must never erase a previously trusted value.

Explicit null handling and source-priority logic will be implemented in a later multi-source phase.

6. Existing compatibility

The existing Luxxy Auto Trader Grok collector, import endpoint, schema version 1, authentication header, response bodies, HTTP statuses, replay handling, suspicious-price review, public stock endpoint and vehicle detail endpoint must remain operational and unchanged.
