# Staff inventory and private service-book photos

The overview's Cars in stock tile opens `/portal?section=inventory`, also available in the Cars navigation section. Staff can search all retained dealership vehicles and filter inventory state. This includes historic sold/archived and source-missing records, so its total can exceed public showroom stock. Each car has preparation tasks, optional staff owner/deadline/internal notes and a link to the existing vehicle activity timeline. These do not change official vehicle facts or imported availability.

Migration 0022 adds three independent private tables. Service-book JPEG bytes live in PostgreSQL, separate from imported galleries. Each car accepts at most three photos, each at most 512,000 bytes and 2,000 pixels per side. Browser capture/select flow scales to 1,600 pixels, re-encodes JPEG at bounded qualities and lets staff review before upload. Unsupported formats show a clear error; phones can use the camera flow or choose JPEG/PNG. Server validates bounded baseline JPEG framing, removes APP/EXIF/XMP and comment metadata, and rejects extra scan metadata. It does not claim photographic authenticity or perform OCR.

Inventory reads/photo downloads require current dealer staff membership. Preparation/photo changes and QR issuance/revocation require `sales.manage` (owners and salespeople). Accounts can read but not write. Tenant filters, composite vehicle/dealer foreign keys and transaction locks prevent cross-dealer records and concurrent cap bypasses. Checklist saves use optimistic revisions.

A QR contains a random 32-byte capability in the URL fragment, scoped to one car/dealer and valid for 15 minutes. Its SHA-256 digest is stored; plaintext is only shown when issued. A new session revokes previous unused sessions for that car. Staff can revoke it explicitly. The phone strips the fragment after reading it and sends `x-service-upload-token` only to same-origin `/api/service-book-upload`. It can inspect the car identity/remaining capacity and submit photos, but cannot read private stored photos or other dealer data. Issuer membership/role is rechecked. Links use the canonical dealer origin. The standalone page avoids showroom stock downloads. Responses have no-store/no-referrer/noindex; tokens are not put into server URLs/logs. The public upload parser caps JSON at 2.2 MB before the global parser.

The phone keeps one UUID request ID and the prepared immutable image strings during submission retries. Backend exact retries return the same saved IDs without another insert. A used session with changed request/body is refused. Expired/revoked sessions are refused. Completed identical retries remain idempotent while the session is not revoked and its issuer remains authorised. Staff list polling is limited to an open QR session and fetches photo metadata, not full images. Authenticated image blobs are fetched separately and their browser object URLs are revoked on unmount.

Checks: `node test-inventory-build.mjs` then `node --test dist-test/staff-inventory.test.mjs` from artifacts/api-server runs all SQL migrations and a fictional two-dealer HTTP integration. `tests/staff-inventory.spec.ts` covers the local mocked phone/tablet/desktop UI and real canvas JPEG resizing. Neither test writes to live records. Live phone/Safari camera testing still needs a human device.

Photos are bounded but accumulate with retained vehicles. PostgreSQL is suitable for this initial small-image feature; consider private object storage and explicit retention policies as the fleet grows. No additional Render service or provider credential is introduced here. Preview UI routes are wired, but functional inventory persistence requires the real authenticated API/database; the local preview's mocked fixture server does not implement these private endpoints.
